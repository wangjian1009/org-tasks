* 定位

Rust bridge 位于 ~harmony~ Cargo crate，与 ~http~ 同为 core 的宿主模块。它把 HarmonyOS 的 N-API 调用转换为结构化请求，调用 core 已有 API，并把响应转换为 JSON；它不是 core 的领域子模块。

* 分层

#+begin_example
ArkTS NativeCoreService
  -> C++ N-API executeCore Promise
  -> harmony C ABI execute
  -> harmony bridge 请求适配
  -> core OrgRepo 与 WebDavSyncPolicy
#+end_example

ArkTS 只传递请求和渲染结果，不解析 org AST、不计算同步决策，也不保存同步领域状态。C++ 只负责参数编组、worker thread、Promise 和字符串资源释放。

* 请求与响应

~HarmonyBridgeRequest~ 当前支持 ~load_repository~ 与 ~sync_webdav~ 两个 action。前者调用 ~OrgRepo.load~ ，后者按既有顺序调用 ~OrgRepo.load~ 、~WebDavSyncPolicy~ 和 ~OrgRepo.sync~ 。这些调用序列属于 Harmony 宿主适配；~OrgRepo~ 、~SyncPolicy~ 、WebDAV 传输和 org 解析算法仍只定义在 core。

响应包含仓库稳定 ID、相对 org 文件路径、原始 UTF-8 内容、字节长度，以及可选同步记录摘要。WebDAV 密码只作为同步请求输入，不能出现在响应、日志或同步记录中。

* 扩展规则

新增查询、编辑或同步能力时，先在 core 定义可复用领域 API 和数据结构；再在 ~harmony/src/bridge.rs~ 添加对应 action；最后扩展 C++ 类型声明和 ~NativeCoreService~ 。不得在 ArkTS、C++ 或 bridge 重写 core 的 org 解析或同步规则。
