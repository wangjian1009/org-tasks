#+TITLE: 废纸篓与系统仓库设计
#+LANGUAGE: zh-CN
#+STARTUP: show2levels

* 范围

APP 启动检查应用沙箱中的系统仓库，缺失时创建，使用随包发布的 ~rawfile/system/trash.org~ 初始化废纸篓；已有内容不覆盖。系统仓库显示名固定为“系统仓库”，出现在笔记本中，只能阅读，不提供修改、同步配置或删除入口，不进入设置的仓库列表。仓库使用 Core 的持久身份，不使用宿主配置 ID 记录恢复来源。

废纸篓使用独立任务视图，复用 ~DataSetManager~ 、 ~DataSet~ 、确认版本、操作队列与页面缓存。右滑无动作，左滑提供归位、清除和批量选择，批量支持归位与清除。清除为不可恢复的永久删除，需确认；归位失败保留原废纸篓条目及说明。

* 删除与来源记录

手机中原有的任务删除改为移入废纸篓，原记录（仅允许没有子节点的记录）在同一 Core 操作组内保存到系统仓库并从来源删除，不能先删除后复制。记录删除时间、源仓库 ID、相对文件路径和父标题路径，备份属性统一使用 SOURCE_ 前缀： ~SOURCE_TIME~ 、 ~SOURCE_FILE~ 、 ~SOURCE_OLPATH~ ，额外增加 ~SOURCE_REPO~ 。路径必须保留特殊字符及重名节点定位，不用拼接分隔符猜测层级。

ID 改存 SOURCE_ID，恢复时还原；仅补入本节点未直接声明的祖先标签，并以 SOURCE_PARENT_TAGS 记录实际复制项，恢复时去除。SOURCE_FILE_TITLE 与 SOURCE_FILE_ID 保存来源文件标题及文件头 ID，无值记为空。恢复按前缀清除所有 SOURCE_ 属性；旧格式不兼容，可清理旧废纸篓记录。

叶节点的原文、属性、状态、规划与日志必须可恢复；任一目标校验或提交失败时，源与废纸篓均保持操作前状态。底层 ~Deletion~ 仍为永久删除，用于清除和过期清理；现有合并、冲突处理内部的删除语义不改变。

* 恢复

恢复按新增任务处理，插入步骤成功后才执行废纸篓来源删除，所有有效修改最终统一存盘，不恢复旧运行时实体身份。原文中的业务 ID、创建时间、状态、规划和正文内容保留，不自动将已完成记录变成待办。当前 Core 插入原位失败就保留废纸篓来源；原仓库、文件或父节点缺失时保留来源，不隐式创建或改投其他父节点；前一兄弟缺失时恢复为父节点的第一个子节点。

* 查询与清理

系统 ~trash.org~ 是特殊文件。今天、计划、随时的任务、候选、计数均在 Core 查询中排除该文件，其他业务查询同样避免将其当作普通任务或移动目标。废纸篓只查询该文件中的独立删除条目，包含已完成任务；当前操作仅支持叶节点。

Core 从独立叶节点自身的 ~SOURCE_TRASH_ID~ 与有效 ~SOURCE_TIME~ 投影可空 ~deletedAt~ ，不继承祖先属性。日期与时刻展示策略均增加 ~Deleted~ ，缺失时不借用创建或关闭时间。废纸篓按删除时间倒序展示。保留天数通过本地 Preferences 的 ~trashRetentionDays~ 配置；默认 30 天，可设置 1 至 3650 天。打开废纸篓或笔记本后由数据管理流程提交过期清理，判断以删除时间为准，不以创建时间或文件修改时间替代；缺失或非法删除时间保留，避免误清除。自动清理复用 Core 查询和永久删除操作，不直接改磁盘。

* 当前实施阶段

Rust 已在原有 TaskOperationGroup 增加 Trash、Restore；主调度器拆分高级操作，每文件 task 自动加载并返回 Metadata，启动后即可接收 Execute，并通过 Discard／Save 处理请求结束。除 Restore 插入失败保留来源外，其他执行失败使整次请求放弃。全部操作结束后由 SaveReady 移交纯字节候选，原统一提交器保存全部文件并通过 channel 确认，各文件 task 生成最终 Metadata 与投影返回后才统一通知。详细消息结构与处理边界见 [[file:../core/废纸篓接口设计.org][任务修改调度与文件任务消息设计]]。

系统仓库初始化、业务查询排除、废纸篓页面、原删除入口切换、设置和过期清理均已接入。侧边栏在日志簿下方提供“废纸篓”；笔记本中的系统仓库文件行打开同一页面。废纸篓只读卡片可展开正文和日志，不允许勾选完成或编辑。列表按删除日期分组，组内保持删除时间倒序，来源行仅展示原分类（region）与项目名（project），以中点分隔；缺少一项时仅显示另一项，两项均缺失时显示“来源未记录”，不展示文件名或路径。

~TrashDataManager~ 通过三个命名 DataSet 查询全部记录、过期记录和文件元信息。过期筛选为 ~deleted.lt.-<保留天数>d~ ，以本地自然日比较；排序为 ~.o.deleted~ ，缺失值始终置末。等待真实首次查询成功后才清理，不依据版本 0 的页面缓存删除；清理与手动清除均通过同一操作组提交，错误时保留记录并提示重试。

每次批量归位或清除只提交一个 ~TaskOperationGroup~ ，携带所选快照的文件版本。界面等待 DataSet 事件归并后核对稳定行身份，成功归位的行消失，原位置不可用的行保留并给出数量提示，多选保留未恢复项。永久清除需二次确认，取消不提交。日志簿原有“恢复为待办”的状态修改语义继续保留，与废纸篓的原位置恢复分别组装。

* 滑动与批量操作共享

废纸篓的单条操作通过 ~TaskSwipeItem~ 配置 ~TaskOperation.RestoreLocation~ 与 ~TaskOperation.Clear~ ，日志簿待办单独使用 ~TaskOperation.SetTodo~ ，不再用页面模式解释同一个 Action。 ~TaskRecordOperations~ 复用已有 Core 操作组语义， ~TaskRecordActionController~ 统一管理确认、提交及归位后保留项核对。 ~TaskSelectionController~ 管理冻结选择快照与批量状态， ~TaskSelectionToolbar~ 复用既有批量操作栏；页面只提供数据集和展示分组，不传入执行回调。过期自动清理仍由 TrashDataManager 负责。

2026-11-18 单条与批量恢复、清除已接入共享操作执行器。专用模拟器核对原状态保留、位置失效保留、多选部分成功后仅失败项继续选中、清除取消零写入及确认后永久删除；日志簿 Reopen 与废纸篓 Restore 的语义独立。
