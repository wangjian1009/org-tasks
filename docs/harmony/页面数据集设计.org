* 范围与职责

今天、收件箱、计划、等待、随时、某天、备忘、日志簿、废纸篓和项目详情均直接使用 DataSet。每个页面声明命名数据集，由 DataSetManager 管理集合、共享连接上下文和页面缓存；每个 DataSet 只持有一个查询，独立消费该查询的订阅结果，并维护任务索引、编辑能力与变化事件。编辑器和项目文档不再创建专用管理器。侧边栏与非任务阅读结果沿用各自的只读管理对象。

DataManager 与原导出名 DataSetManager 共用实现，不提供总事件订阅；它收集各数据集的独立订阅项，一次调用 Workspace.subscribeQuery，并按数据集名保存和清理各订阅 ID。页面通过 dataSet(name) 获取稳定的数据集对象，分别订阅其变化；例如今天页分别订阅 tasks 和 priority，收件箱分别订阅 tasks、recent 和 target。回调只更新关联展示，不根据事件名称再分发，不处理数据版本、operationId 或底层失效事件。

DataSetDefinition 必须声明一个任务或文件元信息 CoreQuery，不再提供宿主 document 查询。管理器将完整文件作为首次加载的一次性返回值交给页面，DataSet 只维护记录与属性。需要配置文件入口时，页面提供纯定义函数；仓库别名通过 ~repositoryBindings~ 在工作线程映射。

收件箱初始化将 tasks、recent、target、files 一次批量订阅；出现与显示生命周期复用同一个初始化 Promise，不各自查询或额外刷新。独立回调只消费该批已取得的结果，首屏等 tasks、recent、target 都取得快照或明确失败后才统一发布界面；回调不会触发第二次读取。最近新增等待主列表首次测量完成后整段显示，读取中或空结果不渲染前置留白及加载占位。已有缓存恢复为版本 0 后按相同边界展示，首次查询完成后再开放编辑。

配置变化由管理器在内部重新配置已有 DataSet，保持对象和页面订阅稳定。用户改变筛选时调用对应 DataSet.setQuery，只重新加载该数据集；旧查询的订阅与迟到结果不能覆盖新查询。页面不重建查询实例或通过总事件回调重新读取数据。

* 核心约束

1. 实际写操作只能由用户显式请求触发；废纸篓保留策略是明确例外，用户打开废纸篓或笔记本时，管理对象等待真实查询结果后按已保存策略清理过期记录，通知回调本身不发起清理。数据集接到用户请求后，先修改直接对应的显示数据，再提交原有底层操作。
2. 乐观显示只更新用户直接修改的字段或条目；重复日期推进、日志、TRIGGER、父任务统计和其他关联变化不在 UI 预测。
3. 数据集收到底层事件，只应用数据变化并通知 UI；事件处理、缓存恢复、属性观察和失败回滚都不能产生写请求。
4. 启动时查询一次；管理类自身操作通过带 operationId 的增量通知确认，提交完成不重新查询。外部更新（其他 operationId 或无编号）由管理类合并触发一次全量刷新，页面不自行查询；Core 查询订阅模块仍不隐式重查。
5. 查询成员资格由 Core 的既有条件能力判断，ArkTS 不重新解释查询语言或 Org。
6. Core 查询订阅为新增模块，复用现有数据变化通知结构；不新增查询专用的 ~QuerySubscriptionChange~ 事件。
7. ~operationId~ 贯穿用户请求、Core 更新通知和页面数据集事件；它用于关联来源，不代表查询成员资格，也不是幂等保证或唯一去重键。

* 数据流

用户请求按如下方向流动：

#+begin_example
用户修改
  -> DataSet 更新用户直接修改的数据
  -> 数据集发布变化，UI 立即刷新
  -> DataSet 显式提交这次用户操作
  -> Core 执行原有修改规则及关联修改
  -> 既有数据变化通知
  -> 新增查询订阅模块按注册条件过滤、归并
  -> DataSet 私有回调应用结果
  -> 数据集发布变化，UI 更新关联显示
#+end_example

底层事件返回路径没有指向提交操作的分支。一个用户请求只产生一次提交；Core 的内部关联处理仍属于原操作，不由数据集追加第二次提交。

启动时先读取本地配置、生成查询定义并恢复磁盘中的已确认快照，然后执行后台配置接入、初始查询与订阅，比较初始结果后发布差异。全局 Workspace 通过同步入口取得；恢复缓存前不调用 ~workspaceFor~ 、 ~Workspace.repos~ 或查询，不等待其他页面的全局用户提交队列。任务与入口元信息缓存都已发布时，页面立即展示版本 0 的只读内容，查询未完成不再显示初始加载圈；首次查询完成后保持当前行身份并开放编辑。初始化快照与开始接收事件之间必须有一致的边界，不能漏掉初始化期间发生的变化。

DataSet 构造当前查询的订阅项及私有 callback，交给 DataSetManager 合并调用，仍独立消费初始结果与范围内增量；同步等旧入口只提供仓库失效时，由该 DataSet 持有的失效监控合并刷新。完整文件仅由管理器分离并作为 start 返回值交给页面，不进入 DataSet。管理器提供共享上下文、批量订阅和按名读取订阅状态，不向页面暴露 Workspace。首次加载及整页刷新各发起一次批量调用；单个查询换代只重建该项，其他数据集不重新读取。配置变化、页面关闭及过期请求返回时，由 Manager 清理对应 ID。

DataSetEvent 包含 insert、remove、update、refresh、ready、complete与 error。事件属于发出它的 DataSet，页面不用按 name 路由。目标记录错误仍以 targetKey 定位，rejectedChanges 保留被拒绝的用户字段；committed 表明已写入但后续确认失败，禁止重复提交。阶段版本和 operationId 由 DataSet 内部维护，页面只展示 data、error 和就绪状态。

同一管理器内的数据集共享操作来源和递增提交阶段；原始增量由各自的查询订阅过滤，不因另一个数据集的同页编辑重复查询。其他页面或 HTTP 的修改由目标 DataSet 合并刷新。全局用户操作队列保证连续提交有序，失败只撤销本次乐观字段，不重放写入。

弹出数据编辑窗口不持有提交函数。日期、标签和重复等控件返回字段修改或修改数组，~startXXX~ 异步接口在确认后返回操作组，取消与页面退出返回空结果。调用点可在确认时提交一次、按变化连续处理，或累积多个结果后交合并入口提交；窗口关闭与持久化成败分开，由调用点维护提交错误与重试。普通任务字段的自动保存策略仍由相应调用点选择。

任务动作的规划与提交分开：编辑器返回完整 ~CoreTaskOperationGroup~ ，滑动组件通过 ~TaskSwipeOperations.submit~ 合并一个或多个组，再调用 ~DataSet.submitOperationGroup~ 。数据集不重写组内的文件版本或操作顺序，提交时分配唯一 ~operationId~ ，按组携带的全部源／目标文件版本排队，并在实际执行前检查订阅范围与启用条件。整个组只产生一次用户提交及完成阶段；空组不推进版本。任务动作组不追加逐条乐观修改，Core 成功事件统一归并快照，失败保留确认数据；组提交错误以操作 ID 为目标上报，不覆盖查询加载状态或使整个列表进入读取失败，批量选择保留供重新选择后重试；缓存仍等待全部在途提交和事件处理结束。

* Core 相关接口

** 操作来源关联

~TaskOperationGroup~ 增加可选 ~operation_id: Option<String>~ ，JSON 字段为 ~operationId~ 。现有提交入口和操作含义不变。

#+begin_src rust
pub struct TaskOperationGroup {
    pub operation_id: Option<String>,
    pub operations: Vec<TaskOperation>,
    pub file_versions: Vec<TaskFileVersion>,
}
#+end_src

同一组操作实际更新多个仓库或引起关联任务变化时，相关数据通知沿用同一个编号。同步、重置、外部更新或旧调用没有编号时使用 ~None~ 。失败或无实际数据变化时，不凭空产生成功更新通知。

** 通用查询订阅模块

新增通用查询订阅模块，维护固定查询条件、已确认成员和订阅生命周期。模块监听既有变化能力，对变化内容按条件过滤和归并，再转发现有 ~DataChangeEvent~ 结构中的数据变化通知。

不新增查询专用事件类型，不改变既有修改规则、事务语义和普通查询行为。订阅句柄可承载初始快照及取消订阅能力；Manager 管理各数据集的独立句柄，页面不可直接接收它的底层事件。

普通任务修改的 ~DataChangeEvent~ 已补充 ~files~ 与 ~changes~ ，包含前后文件元信息、版本、任务快照和位置；修改执行器通过事务内令牌保留移动和改名对应关系，触发器在实际写入处登记事件，不回查数据。Core 查询订阅已完成，Workspace 是统一组合入口，启动时一次返回初始数据与句柄；模块只保留成员 ID、文件版本与分类计数，原始事件不提供公共处理入口。Harmony bridge 与 Today 页面已接入查询订阅；同步、重载等旧入口仍为 ~files=None~ 的仓库失效通知，不能伪装成无变化增量。

** 修改导致查询移除

| 修改前匹配 | 修改后匹配 | 接收范围内的数据变化 |
|-
| 否 | 否 | 不改变成员 |
| 否 | 是 | 新增 |
| 是 | 是 | 更新，必要时调整顺序 |
| 是 | 否 | 从查询结果移除 |

例如将任务从今天改期到明天，原始操作仍是 Modification，今天的数据集移除记录，计划的数据集加入记录，两者沿用同一 ~operationId~ 。查询结果移除不代表 Org 中的实体已删除，更不能转化为新的删除操作。

同一操作可同时产生多个仓库和多条关联变化，不能仅凭见过某个 ~operationId~ 就丢弃后续通知。底层没有成员变化时，也需明确操作确认的完成边界，避免临时创建记录永远停留在界面。

* 实际变更文件识别

调用方不传上传意图仓库列表。Core 以仓库 ID 与相对路径去重，每个业务文件只读取一次、在内存应用全部直接及关联修改，最终只保存一次。事件在修改时登记，提交成功后发布；事件路由不重新读盘，也不创建 outbox。旧同步意图的读取与确认能力保留。临时预览不生成真实仓库事件。

* 版本与阶段结果

1. 从页面缓存恢复的数据统一标为版本 0，不继续使用上次进程的版本计数。缓存中的文件内容版本仍保留，供只读展示与定位。
2. 首次查询结果为版本 1。启动后普通事件与修改完成不会触发查询；显式全量刷新才重新建立订阅，并取得一个新的递增版本。
3. 全量刷新与用户修改的 ~operationId~ 使用 ~dataset/<共享上下文 UUID>/<版本>/<动作>/<查询身份>~ 。刷新编号传入 Harmony 的 ~subscribeQuery~ 并在初始结果中原样回显；初始结果与增量处理都从编号恢复所属版本。刷新换代后的旧订阅回调被丢弃。
4. 每次用户提交形成一个版本，按顺序进入共用提交队列；后续请求只带用户修改的字段。普通字段在真正提交时绑定最新已确认路径与文件版本，改名通过事件的旧新身份映射处理，不从标题猜测路径。
5. 清单、链接、区块和明确的插入位置保留编辑控件的原始文件版本，不能将旧位置引用静默重绑到新文件。普通字段可以基于新快照提交相同字段增量；未修改字段不进入操作组。
6. Core 产生的提交事件先在 C++ 查询监控队列中按顺序交给管理类，再完成修改 Promise。管理类合并事件、移除对应乐观层并发布阶段完成结果；版本 2 完成时，版本 3 排队的字段仍可覆盖在显示层上，但不会污染版本 2 的确认结果。

版本用于识别本管理类的阶段，不代替 Core 文件版本，也不用于丢弃同一操作的其他关联通知。其他实例的操作保留原 ~operationId~ ，按当前订阅阶段应用；查询成员资格始终由 Core 决定。

* 缓存与失败恢复

一个页面一个缓存文件，路径为 ~context.filesDir/page-data/v1/<页面名>.json~ ，页面名由业务固定提供。页面内全部命名数据集在同一个 JSON 对象中保存，不按数据集或查询另建文件。仓库范围、默认配置和固定查询保存在文件内部用于匹配校验，不出现在文件名中；不保存凭据，不写入仓库或同步控制目录。

采用 UTF-8 JSON，数据载荷是对象和数组，不嵌套成 JSON 字符串；读文件一次、 ~JSON.parse~ 一次后构造只读模型。 ~formatVersion~ 是缓存结构版本，与数据集阶段版本分离。文件保留各数据集最后确认版本作为元信息，恢复到新实例时仍统一归零。缓存包含界面所需字段和 Core 给出的状态／优先级答案，不保存 AST，也不把普通 JSON 强制转换为依赖 N-API 绑定的对象。

保存边界为所有已排队的修改提交完成、对应事件已经处理完成。队列未清空时自动保存不会写盘，显式 ~flush()~ 也等待队列清空。不能在一个修改批次中途保存任意阶段；等待结束后一次取得整个页面的已确认快照。临时文件完成完整写入、 ~fsync~ 与关闭后，在原子替换前再次检查没有新修改、确认数据没有变化；否则放弃本次临时文件，等下一个稳定边界重取快照。

只保存确认层，不保存输入草稿或未确认的乐观字段。页面关闭先等待操作与事件，解除订阅以固定关闭边界，再保存；应用退后台调用 ~flushAll()~ 。每个页面文件的写入串行化，同名页面的新实例获得缓存写入权，旧实例稍后关闭不会覆盖新实例的缓存。缓存故障不改变 Core 提交结果；结构损坏、格式或上下文范围不匹配时跳过缓存，继续启动时的查询。每个缓存项另存 queryKey，按对应 DataSet 的查询和仓库绑定签名独立匹配；切换任务筛选只使该数据集缓存失配，未变的范围或文件数据集仍可从版本 0 恢复。

提交失败只撤销对应乐观阶段，保留其他已确认事件与后续排队字段，不自动查询。缺少前序事件或位置版本冲突时停止该次写入并报告错误；用户可显式刷新。发现订阅失效时拒绝当前写入，由管理类按外部失效路径刷新并重建订阅，不自动重放失败操作。

* 编辑控件接入

~TaskEditor~ 直接接收 ~dataSet: DataSet~ 和 ~taskId~ 。数据集已经固定查询范围，组合层只传入对象和稳定行 ID；编辑器不再接收任务副本、查询名称、绑定包装对象或专用管理器。读取、字段修改和记录订阅均调用这个 DataSet。编辑器不注册 Core 全局监听，也不提供回退至逐任务查询的兼容路径。页面列表的稳定行键使用 ~taskKey()~ ，改名、移动和重名序号调整按事件身份映射保留原行；新建临时行确认后继续沿用同一行键，避免控件状态串到另一个同名节点。编辑器未显式传入 ~instanceKey~ 时也使用 DataSet 的稳定行键，保持编辑会话和焦点身份一致。控件分别记录标题和备注的实际修改标记，焦点或关联更新不会把未改的旧字段写回。每次保存只提交变更字段；确认事件中的关联字段由管理类更新。

* 无变化确认与列表稳定性

version 是提交阶段，revision 是显示数据修订号，两者独立。管理层按数据内容比较，不因新对象引用、文件 hash 或版本推进发布数据变化。确认后的内容与本地修改结果一致时，仅完成阶段与缓存，不再次发布 insert、update、remove 或 refresh；ready 仅表示首次查询／刷新已完成，complete 仅表示提交阶段结束，页面不由这两类信号重建列表。

实际字段、查询成员、顺序或关联数据变化时才发布对应数据事件。只比较结构化值，先利用共享引用短路，不在每次修改时序列化全页。文件版本和原文上下文仍保留在最新快照中，下一次编辑由管理对象获取，不能因省略无变化通知而复用过期定位。

今天页忽略文件元信息和纯确认事件；内容字段变化时复用成员和顺序不变的日程、分类与项目容器，不重建列表或更新全页参考时钟。路由替换后通过会话内 PageListPosition 恢复可见项和位置，不把界面滚动状态混入任务 JSON 缓存。

* 跨页面共享通知

通知不属于单个页面数据集。NotificationManager 作为应用级共享类，位于 ~entry/src/main/ets/services/NotificationManager.ets~ ，由 EntryAbility 在启动时调用 start、销毁时调用 stop，退后台不停止，恢复前台补读。管理类只读取通知，DataSetManager 继续负责页面任务与文件快照；编辑器不访问通知管理类或 Core。

启动先注册当前 Workspace 的通知监控，再通过统一查询读取 NotificationQuery。成功提交、同步和其他通知事件在管理类内部合并为通知读取；配置变化重取 Workspace 并解除旧监控。注册、读取和回调均检查生命周期，已停止的实例不能发布迟到结果；读取期间再次失效则丢弃旧结果并读取最新状态。

既有 PageQueryService 批次仍可携带 NotificationQuery，但结果统一交给 NotificationManager 发布；页面批次不再负责注册通知监控。所有读取共用请求序号，旧请求不能覆盖新状态。管理类按通知字段与仓库展示上下文比较，仅内容变化时递增 revision 并写入 AppStorage 的 ~coreNotifications~ ，失败保留最近成功快照。提示由 Core 查询决定，不因本地乐观修改或提交失败预先生成。

各页面在 defineDataSets 中声明命名数据集，创建并启动 DataSetManager，再分别订阅各个 DataSet。需要配置文件入口时，页面将纯定义函数交给管理类，由管理类只根据本地配置调用；缓存读取与恢复由 DataSetManager 完成，各查询的底层调用与句柄清理由 Manager 合并管理，每项记录变化仍由对应 DataSet 独立处理。页面分别消费各 DataSet 的事件和快照，渲染任务、标签候选、入口状态与计划筛选候选。配置变化、缓存恢复和查询换代均在内部处理，页面只刷新关联展示，不处理 scope、版本或总事件分发。重复出现复用当前实例。

收件箱维护 tasks、target、recent、files；未配置入口时不提交无范围 tasks 查询，recent 仍独立可用。某天只维护配置文件的 tasks 与 target，任务通过 ~includeFiles~ 指定同一个 Core 仓库 ID 与相对路径，移除全范围 files 订阅；备忘使用配置文件的 tasks、target、files；有效空文件与失效文件仍通过元信息区分。计划通过 range 维护完整范围，tasks 维护当前筛选查询，选择分类或项目后仅切换 tasks DataSet 的查询；候选始终来自完整范围，选择失效后显示 range 并绑定对应编辑数据集。筛选前先保存编辑，失败保留草稿；快速切换无需等待旧查询，旧结果不能覆盖新范围。新范围快照发布时重建对应控件绑定，避免记录沿用已关闭的数据管理对象。

各个 DataSet 提供自己的查询快照、事件与记录级读写接口，TodayTaskList、PlannedTaskList、LogbookTaskList 不再创建逐记录兼容读取对象。版本 0 恢复只读，初始化完成后才允许编辑；任务编辑器仍立即接收记录事件，页面分组在编辑会话结束后应用。收件箱多选保留进入时的任务与文件版本，不随后台快照改写提交目标；退出选择后消费管理层最新快照。

** 笔记本、文件阅读与同步历史

SnapshotDataManager 为非任务查询结果提供统一的 start、refresh、subscribe、close 生命周期，内部注册当前 Workspace 的变化并合并读取，配置改变重新绑定连接；同步完成也会触发读取，覆盖没有业务文件变化但产生新日志的场景。读取期间发生新变化时丢弃旧结果，失败保留最近成功快照，关闭后清理监控并拒绝迟到发布。该管理对象仅在内存保存快照，不伪装为任务 JSON 缓存。

NotebookDataManager 发布仓库分组与当前配置；FileDataManager 发布普通文件或指定同步历史备份和读取上下文；SyncLogDataManager 发布排序后的同步记录、仓库身份与展示名，展开详情由 SyncLogDetailDataManager 按固定同步 ID 发布完整记录。完整文件、历史与同步规则仍调用既有 Core 接口，管理类不解析 Org。页面的渲染、原文切换、目录定位与展开状态只使用管理对象快照；普通文件变为项目时沿用既有导航。

项目页首次获取文件，随后通过 Task 更新标题与正文，属性修改不重建整个文档；外部更新由管理器合并刷新任务，不重新获取完整文件。项目正文控件只接收修改回调，组合层将回调转交 updateTask，等待管理层确认后取得同版本的新区块与清单 ID；已提交但确认读取失败时保留草稿并阻止重放。通知打开失败后的补读也统一调用 NotificationManager，不由通知控件拼装底层查询。

* 同文件版本推进与废纸篓复用行

DataSet 接收确认文件事件后，同步推进该文件中未修改记录的 ~fileVersion~ ，不能只更新 ~changes~ 中出现的任务。版本不作为显示字段，但任务索引、后续提交和缓存都消费最新确认版本；已选批量快照和位置编辑最初捕获的版本仍保留，用于拒绝过期提交。自动清理后立即恢复也沿用这一规则。

列表以稳定行键复用控件时，侧滑回调按行键从 DataSet 获取当前记录，再打开确认或提交；不能保留首次构造行时的任务快照。进入多选后捕获当时的完整快照，外部变化不悄悄替换选择源版本。废纸篓恢复后等待归并，再按稳定行键核对留存任务，成功行移走，失败行保留选中。
