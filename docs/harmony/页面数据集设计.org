* 范围与职责

今天、收件箱、计划、等待、随时、某天、备忘、日志簿和废纸篓统一消费 AppDataManager 持有的唯一 DataSetManager。收件箱最近新增、笔记本文件列表、侧边栏计数、导航返回判断和角标使用同一应用级数据入口。页面只持有展示状态和自己的监听，不创建基础查询、不读取独立任务页缓存，离开页面不关闭共享实例。项目详情继续按原有独立 DataSetManager 加载完整文档，禁用缓存；完整文件阅读与同步历史仍按需读取。

每个 DataSet 只持有一个查询，独立消费订阅结果并维护任务索引、编辑能力与变化事件；相同基础查询只有一个 DataSet。计划分类／项目筛选和废纸篓过期成员也在应用级管理器构造时创建，并随首次批次建立查询订阅。

DataManager 与原导出名 DataSetManager 共用实现，不提供用于逐任务刷新的总事件订阅；它收集各数据集的独立订阅项，一次调用 Workspace.subscribeQuery，并按数据集名保存和清理各订阅 ID。页面通过 dataSet(name) 获取稳定的数据集对象，分别订阅其变化；例如今天页分别订阅共享的 todayTasks 和 todayPriority，收件箱分别订阅 inboxTasks、inboxRecent 和 inboxFile。回调只更新关联展示，不根据事件名称再分发，不处理数据版本、operationId 或底层失效事件。

管理器可通过 ~options.parent~ 指定父 Manager。 ~dataSet(name)~ 先返回本地同名对象，未定义的名称原样透传父级，继承对象保持原身份、查询订阅与变化通知。父级由创建它的宿主负责启动与关闭；子级的启动、刷新、同步文件事件处理、跨日检查、缓存保存和关闭仅遍历本地数据集，不递归操作父级。通过继承 DataSet 发起编辑或更换查询时，由原所属 Manager 处理。

带父级的页面使用定义数组在构造时声明本地数据集，确保首次按名读取即可区分本地和继承对象；使用定义函数时，构造参数声明全部本地名称。定义函数在 start 读取配置后为既有对象提供查询。纯透传 Manager 可声明空数组，启动与刷新不查询父级。项目页本地仅声明 ~tasks~ 、 ~matches~ 和 ~metadata~ ，查询范围均限定当前文件； ~categories~ 按相同名称从应用级父 Manager 获取，不进入项目首次查询批次，不阻塞项目正文初始化。项目每次打开仍按需读取，禁用页面缓存。

DataSetDefinition 必须声明一个任务或文件元信息 CoreQuery，不再提供宿主 document 查询。管理器将完整文件作为首次加载的一次性返回值交给页面，DataSet 只维护记录与属性。需要配置文件入口时，管理器使用配置定义函数；仓库别名通过 ~repositoryBindings~ 在工作线程映射。

收件箱的 inboxTasks、inboxRecent、inboxFile 与文件元信息随 App 的启动批次加载，组件出现和页面显示只复用初始化 Promise。首屏等三项数据集都取得快照或明确失败后统一发布界面；最近新增等待主列表首次测量完成后整段显示。缓存恢复为版本 0 后按相同边界只读展示，首次查询完成后开放编辑。

配置变化由管理器在内部重新配置已有 DataSet，保持对象和页面订阅稳定。用户改变筛选时调用对应 DataSet.setQuery，只重新加载该数据集；旧查询的订阅与迟到结果不能覆盖新查询。页面不重建查询实例或通过总事件回调重新读取数据。

* 核心约束

1. 实际写操作只能由用户显式请求触发；废纸篓保留策略是明确例外，用户打开废纸篓或笔记本时，管理对象等待真实查询结果后按已保存策略清理过期记录，通知回调本身不发起清理。数据集接到用户请求后，先修改直接对应的显示数据，再提交原有底层操作。
2. 乐观显示只更新用户直接修改的字段或条目；重复日期推进、日志、TRIGGER、父任务统计和其他关联变化不在 UI 预测。
3. 数据集收到底层事件，只应用数据变化并通知 UI；事件处理、缓存恢复、属性观察和失败回滚都不能产生写请求。
4. 启动时查询一次；管理类自身操作通过带 operationId 的增量通知确认，提交完成不重新查询。普通操作组无论 operationId 来自本页或其他入口，都由既有查询订阅应用增量。同步和 reset 的 ExternalFileChanged 由 DataSetManager 按文件范围选择数据集并合并一次刷新；页面不自行查询，Core 查询订阅模块仍不隐式重查。
5. 查询成员资格由 Core 的既有条件能力判断，ArkTS 不重新解释查询语言或 Org。
6. Core 查询订阅为新增模块，复用现有数据变化通知结构；不新增查询专用的 ~QuerySubscriptionChange~ 事件。
7. ~operationId~ 贯穿用户请求、Core 更新通知和页面数据集事件；它用于关联来源，不代表查询成员资格，也不是幂等保证或唯一去重键。

* 数据流

用户请求按如下方向流动：

#+begin_example
用户修改
  -> DataSet 更新用户直接修改的数据
  -> 数据集发布变化，UI 立即刷新
  -> DataSet 显式提交这次用户操作
  -> Core 执行原有修改规则及关联修改
  -> 既有数据变化通知
  -> 新增查询订阅模块按注册条件过滤、归并
  -> DataSet 私有回调应用结果
  -> 数据集发布变化，UI 更新关联显示
#+end_example

底层事件返回路径没有指向提交操作的分支。一个用户请求只产生一次提交；Core 的内部关联处理仍属于原操作，不由数据集追加第二次提交。

启动时先读取本地配置、生成查询定义并恢复磁盘中的已确认快照，然后执行后台配置接入、初始查询与订阅，比较初始结果后发布差异。全局 Workspace 通过同步入口取得；恢复缓存前不调用 ~workspaceFor~ 、 ~Workspace.repos~ 或查询，不等待其他页面的全局用户提交队列。任务与入口元信息缓存都已发布时，页面立即展示版本 0 的只读内容，查询未完成不再显示初始加载圈；首次查询完成后保持当前行身份并开放编辑。初始化快照与开始接收事件之间必须有一致的边界，不能漏掉初始化期间发生的变化。

DataSet 构造当前查询的订阅项及私有 callback，交给 DataSetManager 合并调用，仍独立消费初始结果与范围内增量；外部文件监控与跨日检查由 DataSetManager 统一持有，DataSet 不再逐个注册全局失效监控或刷新定时器。完整文件由管理器分离：首次作为 start 返回值交给宿主，外部失效恢复时交付 subscribeFiles 接收者，不进入 DataSet。管理器提供共享上下文、批量订阅和按名读取订阅状态，不向页面暴露 Workspace。首次加载及整页刷新各发起一次批量调用；单个查询换代只重建该项，其他数据集不重新读取。配置变化、页面关闭及过期请求返回时，由 Manager 清理对应 ID。

DataSetEvent 包含 insert、remove、update、refresh、ready、complete与 error。事件属于发出它的 DataSet，页面不用按 name 路由。目标记录错误仍以 targetKey 定位，rejectedChanges 保留被拒绝的用户字段；committed 表明已写入但后续确认失败，禁止重复提交。阶段版本和 operationId 由 DataSet 内部维护，页面只展示 data、error 和就绪状态。

同一管理器内的数据集共享操作来源和递增提交阶段；原始增量由各自的查询订阅过滤，不因另一个数据集的同页编辑重复查询。其他页面或 HTTP 的修改由目标 DataSet 合并刷新。全局用户操作队列保证连续提交有序，失败只撤销本次乐观字段，不重放写入。

弹出数据编辑窗口不持有提交函数。日期、标签和重复等控件返回字段修改或修改数组， ~startXXX~ 异步接口在确认后返回操作组，取消与页面退出返回空结果。调用点可在确认时提交一次、按变化连续处理，或累积多个结果后交合并入口提交；窗口关闭与持久化成败分开，由调用点维护提交错误与重试。普通任务字段的自动保存策略仍由相应调用点选择。

任务动作的规划与提交分开：编辑器返回完整 ~CoreTaskOperationGroup~ ，滑动组件通过 ~TaskSwipeOperations.submit~ 合并一个或多个组，再调用 ~DataSet.submitOperationGroup~ 。数据集先按组内的 Modification、Deletion 和 Trash 操作合并本地覆盖层并发布变化，UI 随即从 DataSet 读取到修改后的快照；提交在后台按文件排队，不把界面操作绑定到 Core Promise。每组分配唯一 ~operationId~ ，实际执行前按确认快照重取文件版本，使同一文件的连续修改可以保留并衔接。确认事件到达后移除对应覆盖操作、推进文件版本并继续提交下一个操作；失败只移除本次覆盖并保留后续操作。空组不推进版本，组提交错误以操作 ID 为目标上报，不覆盖查询加载状态或使整个列表进入读取失败；缓存仍等待全部在途提交和事件处理结束。

* 等待任务启动动作

等待页左滑菜单复用通用 ~TaskOperation.ToggleState~ ，显示“开始”并由 ~TaskEditor.start~ 生成同一操作组。状态从等待转为进行中时，通用规则检查源任务的 ~SCHEDULE~ ：缺失或晚于设备本地日期时追加当天计划日期；已有今天或过去日期保持不变。TODO 与 SCHEDULE 修改在同一文件版本和同一提交组中完成，失败整体回滚，其他字段由 Core 保留。

* Core 相关接口

** 操作来源关联

~TaskOperationGroup~ 增加可选 ~operation_id: Option<String>~ ，JSON 字段为 ~operationId~ 。现有提交入口和操作含义不变。

#+begin_src rust
pub struct TaskOperationGroup {
    pub operation_id: Option<String>,
    pub operations: Vec<TaskOperation>,
    pub file_versions: Vec<TaskFileVersion>,
}
#+end_src

同一组操作实际更新多个仓库或引起关联任务变化时，相关数据通知沿用同一个编号。同步、重置、外部更新或旧调用没有编号时使用 ~None~ 。失败或无实际数据变化时，不凭空产生成功更新通知。

** 通用查询订阅模块

新增通用查询订阅模块，维护固定查询条件、已确认成员和订阅生命周期。模块监听既有变化能力，对变化内容按条件过滤和归并，再转发现有 ~DataChangeEvent~ 结构中的数据变化通知。

不新增查询专用事件类型，不改变既有修改规则、事务语义和普通查询行为。订阅句柄可承载初始快照及取消订阅能力；Manager 管理各数据集的独立句柄，页面不可直接接收它的底层事件。

** 修改导致查询移除

| 修改前匹配 | 修改后匹配 | 接收范围内的数据变化 |
|-
| 否 | 否 | 不改变成员 |
| 否 | 是 | 新增 |
| 是 | 是 | 更新，必要时调整顺序 |
| 是 | 否 | 从查询结果移除 |

例如将任务从今天改期到明天，原始操作仍是 Modification，今天的数据集移除记录，计划的数据集加入记录，两者沿用同一 ~operationId~ 。查询结果移除不代表 Org 中的实体已删除，更不能转化为新的删除操作。

同一操作可同时产生多个仓库和多条关联变化，不能仅凭见过某个 ~operationId~ 就丢弃后续通知。底层没有成员变化时，也需明确操作确认的完成边界，避免临时创建记录永远停留在界面。

* 实际变更文件识别

调用方不传上传意图仓库列表。Core 以仓库 ID 与相对路径去重，每个业务文件只读取一次、在内存应用全部直接及关联修改，最终只保存一次。事件在修改时登记，提交成功后发布；事件路由不重新读盘，也不创建 outbox。旧同步意图的读取与确认能力保留。临时预览不生成真实仓库事件。

* 版本与阶段结果

1. 从页面缓存恢复的数据统一标为版本 0，不继续使用上次进程的版本计数。缓存中的文件内容版本仍保留，供只读展示与定位。
2. 首次查询结果为版本 1。启动后普通事件与修改完成不会触发查询；显式全量刷新才重新建立订阅，并取得一个新的递增版本。
3. 全量刷新与用户修改的 ~operationId~ 使用 ~dataset/<共享上下文 UUID>/<版本>/<动作>/<查询身份>~ 。刷新编号传入 Harmony 的 ~subscribeQuery~ 并在初始结果中原样回显；初始结果与增量处理都从编号恢复所属版本。刷新换代后的旧订阅回调被丢弃。
4. 每次用户提交形成一个版本，按顺序进入共用提交队列；后续请求只带用户修改的字段。普通字段在真正提交时绑定最新已确认路径与文件版本，改名通过事件的旧新身份映射处理，不从标题猜测路径。
5. 清单、链接、区块和明确的插入位置保留编辑控件的原始文件版本，不能将旧位置引用静默重绑到新文件。普通字段可以基于新快照提交相同字段增量；未修改字段不进入操作组。
6. Core 产生的提交事件先在 C++ 查询监控队列中按顺序交给管理类，再完成修改 Promise。管理类合并事件、移除对应乐观层并发布阶段完成结果；版本 2 完成时，版本 3 排队的字段仍可覆盖在显示层上，但不会污染版本 2 的确认结果。

版本用于识别本管理类的阶段，不代替 Core 文件版本，也不用于丢弃同一操作的其他关联通知。其他实例的操作保留原 ~operationId~ ，按当前订阅阶段应用；查询成员资格始终由 Core 决定。

* 缓存与失败恢复

每个独立管理器一个缓存文件，路径为 ~context.filesDir/page-data/v1/<页面名>.json~ ，名称由业务固定提供；普通任务页统一使用 app，旧的各页缓存不再读取。管理器内全部命名数据集在同一个 JSON 对象中保存，不按数据集或查询另建文件。仓库范围、默认配置和固定查询保存在文件内部用于匹配校验，不出现在文件名中；不保存凭据，不写入仓库或同步控制目录。

采用 UTF-8 JSON，数据载荷是对象和数组，不嵌套成 JSON 字符串；读文件一次、 ~JSON.parse~ 一次后构造只读模型。 ~formatVersion~ 是缓存结构版本，与数据集阶段版本分离。文件保留各数据集最后确认版本作为元信息，恢复到新实例时仍统一归零。缓存包含界面所需字段和 Core 给出的状态／优先级答案，不保存 AST，也不把普通 JSON 强制转换为依赖 N-API 绑定的对象。

保存边界为所有已排队的修改提交完成、对应事件已经处理完成。队列未清空时自动保存不会写盘，显式 ~flush()~ 也等待队列清空。不能在一个修改批次中途保存任意阶段；等待结束后一次取得整个页面的已确认快照。临时文件完成完整写入、 ~fsync~ 与关闭后，在原子替换前再次检查没有新修改、确认数据没有变化；否则放弃本次临时文件，等下一个稳定边界重取快照。

只保存确认层，不保存输入草稿或未确认的乐观字段。页面关闭先等待操作与事件，解除订阅以固定关闭边界，再保存；应用退后台调用 ~flushAll()~ 。每个页面文件的写入串行化，同名页面的新实例获得缓存写入权，旧实例稍后关闭不会覆盖新实例的缓存。缓存故障不改变 Core 提交结果；结构损坏、格式或上下文范围不匹配时跳过缓存，继续启动时的查询。每个缓存项另存 queryKey，按对应 DataSet 的查询和仓库绑定签名独立匹配；切换任务筛选只使该数据集缓存失配，未变的范围或文件数据集仍可从版本 0 恢复。

提交失败只撤销对应乐观阶段，保留其他已确认事件与后续排队字段，不自动查询。缺少前序事件或位置版本冲突时停止该次写入并报告错误；用户可显式刷新。发现订阅失效时拒绝当前写入，由管理类按外部失效路径刷新并重建订阅，不自动重放失败操作。

任务快照与缓存保留 ~appLinks~ 数组；旧缓存缺失时恢复为空数组。编辑器直接读取已有快照，不额外复制完整任务或触发查询。

* 编辑控件接入

~TaskEditor~ 直接接收 ~dataSet: DataSet~ 和 ~taskId~ 。数据集已经固定查询范围，组合层只传入对象和稳定行 ID；编辑器不再接收任务副本、查询名称、绑定包装对象或专用管理器。读取、字段修改和记录订阅均调用这个 DataSet。编辑器不注册 Core 全局监听，也不提供回退至逐任务查询的兼容路径。页面列表的稳定行键使用 ~taskKey()~ ，改名、移动和重名序号调整按事件身份映射保留原行；新建临时行确认后继续沿用同一行键，避免控件状态串到另一个同名节点。编辑器未显式传入 ~instanceKey~ 时也使用 DataSet 的稳定行键，保持编辑会话和焦点身份一致。控件分别记录标题和备注的实际修改标记，焦点或关联更新不会把未改的旧字段写回。每次保存只提交变更字段；确认事件中的关联字段由管理类更新。

各任务页面直接提供 AppDataManager 的共享 DataSet 给编辑控件。缓存版本 0 阶段只读，首次查询完成后开放编辑；离开页面只解除展示监听，全局实例与稳定记录身份保持。所有普通任务页共用一个文件监控与跨日检查器，由 Manager 合并外部变化并刷新受影响查询。分类、项目分组和编辑会话中的重排延后规则保持原有行为。

计划全部范围由 planned 提供。plannedFiltered 在启动批次使用基础查询，选中分类或项目后替换其查询。清除选择或候选消失时，页面直接使用 planned。离开页面只移除展示监听。切换筛选以请求序号隔离迟到结果。

废纸篓列表使用 trash。trashExpired 根据本地保留天数随启动批次查询。打开废纸篓或笔记本时重新确认保留天数，设置有变化时替换既有查询。只有真实查询完成且版本大于 0 后才执行清理。并发打开共用一次清理，失败保留记录供重试。

* APP 外部数据验证入口

APP 仅在显式测试启动参数开启时提供内嵌 HTTP 查询和批量修改接口；正常图标启动不监听，不提供设置开关、不持久化。使用当前 UI Workspace 的 API 操作触发真实事件，随后各页面管理类刷新自己的数据集或完整阅读快照；界面不把收到的变化再次提交。接口约定见 [[file:../core/APP内嵌HTTP接口.org][APP 内嵌 HTTP 接口]]。

* 无变化确认与列表稳定性

version 是提交阶段，revision 是显示数据修订号，两者独立。管理层按数据内容比较，不因新对象引用、文件 hash 或版本推进发布数据变化。确认后的内容与本地修改结果一致时，仅完成阶段与缓存，不再次发布 insert、update、remove 或 refresh；ready 仅表示首次查询／刷新已完成，complete 仅表示提交阶段结束，页面不由这两类信号重建列表。

实际字段、查询成员、顺序或关联数据变化时才发布对应数据事件。只比较结构化值，先利用共享引用短路，不在每次修改时序列化全页。文件版本和原文上下文仍保留在最新快照中，下一次编辑由管理对象获取，不能因省略无变化通知而复用过期定位。

今天页忽略文件元信息和纯确认事件；内容字段变化时复用成员和顺序不变的日程、分类与项目容器，不重建列表或更新全页参考时钟。路由替换后通过会话内 PageListPosition 恢复可见项和位置，不把界面滚动状态混入任务 JSON 缓存。

** 调用点与共享生命周期

所有普通任务页面复用 AppDataManager 的 DataSetManager，查询定义集中维护；收件箱正文与最近新增分别使用 inboxTasks 与 inboxRecent。项目文档另建无缓存 Manager 并通过 parent 共享分类候选。所有 TaskEditor 入口显式注入 dataSet 和稳定行 taskId。

滚动记录使用可见项身份与局部偏移，插入同步提示等前置行不会使保存的阅读位置指向另一条任务；布局空闲回调不覆盖用户滚动结果。

* 项目详情：一次性文件与任务局部更新

项目页创建 ~DataManager~ ，显式指定 ~cache: false~ 。每次打开重新启动查询订阅：使用空表达式获取全部标题， ~includeFiles~ 与 ~fullFiles~ 指向真实 Core 仓库和目标路径， ~includeIgnored: true~ 保留已打开文件的全部可编辑标题。任务、普通标题、完成与取消节点均保留，冲突子树继续按 Core 规则排除。

~start(): Promise<DataLoadResult[]>~ 返回命名查询的一次性文件数组，管理器在交给 DataSet 前移除完整文件。首次成功后不保存文件或包含文件的已完成 Promise；普通任务增量不再请求 ~fullFiles~ ；管理器检测到外部失效时，可向注册 ~subscribeFiles~ 的宿主一次性交付新的完整文件，完整文件仍不进入 DataSet 或缓存。页面从文件提取导言、文件标签、源文本与文档分段，用完整 ~path~ 关联 Task，随后释放文件对象；查看原文使用本次打开时的源文本，显式“刷新项目”开启新的阅读会话重新取得一次完整文件；会话身份驱动文档组件重建，即使文件版本相同也重新绑定新 DataSet，并恢复阅读偏移。

DataSet 不提供 document、getFile 或完整文件事件，普通提交不进行文件确认重读；外部失效恢复由 Manager 管理。编辑统一使用 updateTask，Core 的原始提交事件维护改名、移动和重名出现序号的映射，控件按稳定行 ID 订阅 Task。每个 ProjectTaskSection 直接取得 ~taskSource(rowId)~ 并注册 Monitor，维护自己的标题与段落；退出时取消。Task 的实际字段变化只驱动该章节，页面不接收整批变化后再遍历分发；正文从 Task.editContent.blocks 取得。只有来源更新而可见内容相同时，新正文会话直接读取来源中的最新文件版本，不依赖尚未重绘的 node；草稿进入编辑后冻结源版本，提交继续携带该版本，外部变化后不能静默覆盖。位置 ID 与文件版本仅更新编辑上下文，可见正文未变化时保留 HTML 修订号；属性修改不重建文档容器或其他章节。

新增、删除及顺序变化只调整受影响章节的成员；保留其他章节实例和滚动位置。目录打开时读取最新任务名称与状态。编辑会话期间延迟应用章节外部快照，结束后应用最新 Task，避免打断草稿；失败沿用原有定向回滚和禁止重复提交规则。页级阅读状态与任务数据缓存分离，不读取或写入 page-data 目录。flush 仍等待提交及事件确认。

* 跨页面共享通知

通知不属于单个页面数据集。NotificationManager 作为应用级共享类，位于 ~entry/src/main/ets/services/NotificationManager.ets~ ，由 EntryAbility 在启动时调用 start、销毁时调用 stop。订阅跨前后台持续接收增量，恢复前台只重试异常订阅。管理类只消费通知列表，DataSetManager 继续负责页面任务与文件快照；编辑器不访问通知管理类或 Core。

启动注册当前 Workspace 的通知列表订阅，Core 默认推送首次完整列表，后续列表变化才回调。配置变化重新绑定订阅范围，旧生命周期回调被忽略。基线与文件版本比较由 Core 文件服务负责，通知处理任务维护各文件和仓库的通知贡献，见 [[file:../core/通知订阅设计.org][通知订阅设计]]。

PageQueryService 批次只包含任务和文件。NotificationManager 按列表回调发布共享快照，宿主仓库展示映射或内容变化才推进 AppStorage revision；订阅失败保留最近成功快照，页面查询失败不影响通知。设备角标从推送的快照更新内存冲突计数，后台同步收尾复用该计数写入角标。

今天页直接消费共享通知快照，列表始终保留通知项，无通知时高度为零，避免插入或删除列表槽位影响后续输入焦点。通知插入、移除或高度变化时，已滚动的列表按当前可见稳定记录补偿位置；停在顶部时直接展示新提示，不将其滚出屏幕。页面离开后取消迟到补偿。通知刷新不重建任务数据集、不结束编辑会话，也不覆盖输入草稿。其他页面复用同一快照，无需通过打开抽屉或切换页面才能看到待同步提示。

退后台时，后台服务在短时任务保护内调用 DataSetManager.flushAll，等待已提交的修改、事件归并和缓存保存。缓存失败记录错误后继续。随后通过 ~NotificationManager.subscribe~ 接收当前绑定的共享快照，收到快照或短时任务到期即解除订阅。仅共享快照包含待同步通知时才读取同步配置，启用 WebDAV 后方可启动新会话。已有同步会话继续受到后台保护。

* 侧边栏：共享数据集与只读投影

SidebarDataManager 只投影 AppDataManager 的命名 DataSet，不查询 Core、不注册文件监控、不持有侧边栏缓存。AppShell 订阅其只读快照，显示计数、今天关注徽标、入口状态和项目分组。打开抽屉调用的 start 复用全局初始化 Promise，关闭只移除本侧边栏的订阅。

今天计数直接使用 todayTasks 的任务数量，与今天页是同一个 DataSet，不受页面标签筛选影响。关注计数、计划、随时、等待、日志簿、废纸篓与三个配置入口各有固定 Core 查询；项目查询为完整范围的 FileQuery.isProject，不按缓存项目列表缩小范围。文件身份、忽略规则、成员资格与排序由 Core 维护；宿主只读取结果数量、组合分区和映射入口状态。

通知由 Core 列表回调交给 NotificationManager，侧边栏不另存通知。AppShell 从 RegionOrderService 读取共享排序偏好，只重排已有项目快照，不重建查询。数据集读取失败保留确认快照并展示错误，再次打开时把失败数据集合并重试；正常重开不查询。关闭抽屉不影响全局数据集继续更新，重开直接显示最新数据。

* 全部页面退出外壳刷新机制

AppShell 只组合标题栏、导航和下拉同步，不注册 Workspace 监控、广播数据版本、触发正文读取或按抽屉开合延迟刷新。

** 任务页面

各页面在 defineDataSets 中声明命名数据集，创建并启动 DataSetManager，再分别订阅各个 DataSet。需要配置文件入口时，页面将纯定义函数交给管理类，由管理类只根据本地配置调用；缓存读取与恢复由 DataSetManager 完成，各查询的底层调用与句柄清理由 Manager 合并管理，每项记录变化仍由对应 DataSet 独立处理。页面分别消费各 DataSet 的事件和快照，渲染任务、标签候选、入口状态与计划筛选候选。配置变化、缓存恢复和查询换代均在内部处理，页面只刷新关联展示，不处理 scope、版本或总事件分发。重复出现复用当前实例。

收件箱维护 tasks、target、recent、files；未配置入口时不提交无范围 tasks 查询，recent 仍独立可用。某天只维护配置文件的 tasks 与 target，任务通过 ~includeFiles~ 指定同一个 Core 仓库 ID 与相对路径，移除全范围 files 订阅；备忘使用配置文件的 tasks、target、files；有效空文件与失效文件仍通过元信息区分。计划通过 range 维护完整范围，tasks 维护当前筛选查询，选择分类或项目后仅切换 tasks DataSet 的查询；候选始终来自完整范围，选择失效后显示 range 并绑定对应编辑数据集。筛选前先保存编辑，失败保留草稿；快速切换无需等待旧查询，旧结果不能覆盖新范围。新范围快照发布时重建对应控件绑定，避免记录沿用已关闭的数据管理对象。

各个 DataSet 提供自己的查询快照、事件与记录级读写接口，TodayTaskList、PlannedTaskList、LogbookTaskList 不再创建逐记录兼容读取对象。版本 0 恢复只读，初始化完成后才允许编辑；任务编辑器仍立即接收记录事件，页面分组在编辑会话结束后应用。收件箱多选保留进入时的任务与文件版本，不随后台快照改写提交目标；退出选择后消费管理层最新快照。

收件箱批量修改、移动、合并、快速录入及日志簿删除／恢复统一经所属 DataSet.operate 进入共享用户队列。它分配递增阶段与 operationId，复用原业务服务生成普通 Core 操作，确认通过查询订阅增量归并；成功不再重新查询。排队字段接收前序操作产生的真实身份映射，失败不生成补偿写入；操作及事件完成后才保存确认缓存。

** 笔记本、文件阅读与同步历史

SnapshotDataManager 为非任务查询结果提供统一的 start、refresh、subscribe、close 生命周期，内部注册当前 Workspace 的变化并合并读取，配置改变重新绑定连接；同步完成也会触发读取，覆盖没有业务文件变化但产生新日志的场景。读取期间发生新变化时丢弃旧结果，失败保留最近成功快照，关闭后清理监控并拒绝迟到发布。该管理对象仅在内存保存快照，不伪装为任务 JSON 缓存。

NotebookDataManager 发布仓库分组与当前配置；FileDataManager 发布普通文件或指定同步历史备份和读取上下文；SyncLogDataManager 发布排序后的同步记录、仓库身份与展示名，展开详情由 SyncLogDetailDataManager 按固定同步 ID 发布完整记录。完整文件、历史与同步规则仍调用既有 Core 接口，管理类不解析 Org。页面的渲染、原文切换、目录定位与展开状态只使用管理对象快照；普通文件变为项目时沿用既有导航。

项目页首次获取文件，随后通过 Task 更新标题与正文，属性修改不重建整个文档；来自同一 Workspace 的 UI／HTTP 操作由完整任务事件直接归并；同步、reset 或磁盘外部失效由管理器合并刷新，项目宿主注册的一次性文件接收者同时取得最新导言和链接索引。项目正文控件只接收修改回调，组合层将回调转交 updateTask，等待管理层确认后取得同版本的新区块与清单 ID；已提交但确认读取失败时保留草稿并阻止重放。通知打开失败后的重新订阅也统一调用 NotificationManager，不由通知控件拼装底层查询。

* 按文件衔接修改

用户字段编辑按 ~repoId~ 与文件相对路径衔接，先合并到 DataSet 覆盖层并立即返回；同一文件的后续提交进入文件队列，前一事件确认后用最新确认快照组装路径和版本，必要时重取单文件 hash；没有前序排队修改的位置编辑继续保留控件捕获的源版本，过期时拒绝提交；不同文件的编辑可同时提交。移动同时占用源、目标文件，批量操作按当前数据集文件范围与字段编辑衔接。刷新读取按当前文件范围与编辑衔接，不再进入全局串行 Promise 队列，真实查询、修改和同步的先后关系由 Core 命令调度统一保证。

全局空闲判断仅跟踪全部在途与排队请求，缓存保存、关闭和退后台等待其排空；某次修改失败只移除自身乐观层，不阻止后续文件请求。Core 返回前仍确认通知处理，C++ 在完成修改 Promise 前归并已排队查询事件。

* 正文区块的展示差异

任务与项目正文统一由 ~TaskContentEditor~ 管理。数据集只投递任务快照；共享正文控件在内部对比区块的类型、内容与定位，维持独立于数组索引的控件身份。未变化区块重用原引用，头部插入、删除、重排或定位偏移不销毁其他阅读节点。

文件版本仍传递给链接与区块编辑的校验上下文，不作为正文重载条件。只有区块 HTML 真正变化才更新对应 WebView；任务状态底色由外壳绘制，正文持续透明。语法拆分仍由 Core 负责；嵌套逻辑树的具体投影扩展见 [[file:TaskContentEditor设计.org][TaskContentEditor 设计]]，尚待 Core 对外接口方案确认。

* 项目文件头编辑

现有文件元信息快照增加 fileVersion 与 headerEntries，项目页通过 metadata 数据集持续取得同版本条目。区域内所有字段以同一 sourceVersion 批量提交已修改项，TAGS／FILETAGS 使用标签数组值。DataSet.updateFileHeader(file, changes, sourceVersion) 复用 operate、UserOperationQueue、原 Workspace 操作组和来源关联；FileHaderModification 必须提交显式版本，不能借任务按最新版本保存的策略覆盖文件头旧草稿。

外部属性更新由 Core 发出文件元信息与同文件任务投影，数据集分别归并，页面只刷新展示。整个属性区共用一次 TaskInlineSession，输入独立于确认快照；编辑中继续更新 headerEntries 与 headerVersion，推迟文档结构刷新。文件版本变化后保留草稿并提示重新编辑，不替换原 ID 自动重试。空项目的文件事件不能因缺少任务变化而忽略。完整接口见 [[file:../core/文件头属性编辑设计.org][文件头属性编辑设计]]。

* 同文件版本推进与废纸篓复用行

DataSet 接收确认文件事件后，同步推进该文件中未修改记录的 ~fileVersion~ ，不能只更新 ~changes~ 中出现的任务。版本不作为显示字段，但任务索引、后续提交和缓存都消费最新确认版本；已选批量快照和位置编辑最初捕获的版本仍保留，用于拒绝过期提交。自动清理后立即恢复也沿用这一规则。

列表以稳定行键复用控件时，侧滑回调按行键从 DataSet 获取当前记录，再打开确认或提交；不能保留首次构造行时的任务快照。进入多选后捕获当时的完整快照，外部变化不悄悄替换选择源版本。废纸篓恢复后等待归并，再按稳定行键核对留存任务，成功行移走，失败行保留选中。

* 外部文件变化的按范围刷新

~DataSetManager~ 只根据查询的仓库与文件范围判断是否需要刷新，不在 ArkTS 解释任务表达式、标签、分类或完成状态。有限 ~includeFiles~ 与变化文件无交集时跳过； ~excludeFiles~ 排除的文件不触发该项；没有文件包含限制的查询必须刷新，不能以当前结果为空或未包含变化文件为由跳过。宿主仓库别名先按 ~repositoryBindings~ 与 Core 仓库身份映射，不能把配置 ID 直接与事件 Core ID 比较。

连续事件收集受影响的数据集名；一次调用并发请求这些数据集刷新，由 Manager 的订阅收集器合并成一次 ~subscribeQuery~ ，同批共享一次扫描。刷新期间到达的新事件排入下一批；配置换代、旧查询回调及页面关闭沿用 generation 与 identity 检查。保存页面缓存前等待外部刷新和写操作收尾；关闭释放文件监控与跨日定时器。

跨日刷新、主动刷新和失败重试执行具有有效查询范围的数据集。尚未配置入口文件的数据集持有空快照。

~DataSet~ 接收新快照后比较结构化内容，只对实际成员与字段变化发布 ~insert~ 、 ~remove~ 、 ~update~ 或混合 ~refresh~ ；内容相同只推进确认版本，不重复发布数据变化。通知模块不监听外部文件事件：Core 已按通知条件刷新并广播列表， ~NotificationManager~ 只消费通知订阅结果。Core 事件与运行时模型见 [[file:../core/外部文件变化监控设计.org][外部文件变化监控设计]] 。

* 启动读取边界

纯本地冷启动时，全部普通任务页、最近新增、笔记本、侧边栏、导航计数和角标的基础查询共享一次初始批次；启动同步只接入已有 Workspace，角标刷新只读取共享确认快照，因此这些业务每仓库只扫描一次。Core 文件服务启动只加载基线控制元数据，通知初始化不扫描或读取 Org 正文；WebDAV 启动检查读取基线和远端元数据，本地工作树扫描为零。实际同步通常在下载和合并阶段各扫描一次本地工作树，两次扫描之间允许普通编辑。重置另遍历目录收集删除路径，不为此读取正文。同步或重置改变工作文件时，共享 Manager 将受影响的查询合并为后续批次，每批对查询覆盖的仓库扫描一次。普通任务提交复用受影响文件的提交结果，通知增量增加零次扫描。首次通知缓存与增量契约见 [[file:../core/通知订阅设计.org][通知订阅设计]]。

* 应用关联数据集

~AppDataManager~ 通过 ~appLinkTasks~ 共享订阅 ~has.app~ ，沿用系统废纸篓排除及任务缓存规则。设置页读取任务快照中的 ~appLinks~ ，匹配已配置的目录名称或别名，再以链接名称与 Preferences 中的全部关联去重合并，应用安装状态由 HarmonyOS 查询。任务增删改通过 DataSet 更新引用列表，已有绑定仍保留在 Preferences 中。

* 全局提醒管理数据集

~AppDataManager~ 在唯一应用 DataSetManager 中注册 ~reminderTasks~ ，查询 ~it.todo has.reminder o.reminder~ ，与普通页面共享首次批次、Workspace 和外部文件监听。通过 ~uncachedDataSets~ 将该数据集排除于磁盘写入及恢复，其他基础数据集保持版本零缓存恢复规则。~ReminderManager.register(context, source)~ 绑定唯一来源并订阅变更，不创建第二个 DataSetManager；设置列表消费同一实例，离开页面只解除自身订阅。

全局数据层启动后异步启动提醒维护，不等待系统日历操作才显示任务。首次已确认快照加载后执行一次系统日历库存核对；之后确认事件驱动新增、修改与移出的增量维护，complete 阶段同样处理，忽略乐观写入。来源错误或失效使旧批次停止，保留已有事件；重新确认后继续维护。AppDataManager 关闭时先停止提醒订阅与维护，再关闭共享查询。

~ReminderManager~ 同时封装提醒设置、授权、状态订阅和 ~checkRegistered(task)~ 。展开卡片的单项核实等待已有维护完成，再异步读取系统事件；不以应用内存状态替代系统事实，也不发起 Core 查询或日历写入。展开、改期、收起和退出的结果接收边界见 [[file:任务提醒设计.org][任务提醒设计]]。

* 稳定行的 TaskDataSource 与 Monitor

每个 TaskEditor 在出现时取得所属 DataSet 的 ~taskSource(rowId)~ ，向返回的 ~TaskDataSource~ 注册一个 Monitor，消失时取消。DataSet 以稳定行 ID 保存来源对象；Core 增量先更新数据索引、合并所有待提交修改，再将新快照直接交给对应来源，不再向每个编辑器广播 DataSetEvent 后分别定位记录。

来源对象保存当前可编辑快照。首次注册交付一次快照；新增或删除通过列表事件创建、移除行，已有记录来源独立处理新增后的恢复、更新、移除及定向错误。改名或移动后，Core 前后身份映射保留稳定行和来源对象；确认删除或离开查询范围后关闭旧来源，同名重建使用新来源，不承接旧编辑。 ~watchTask~ 作为兼容入口委托同一个来源，不增加底层订阅。

来源先更新本批全部记录的指针，再交付可见变化。只有文件版本或编辑上下文变化时，来源仍取得新快照，后续操作直接读取最新路径和版本；可见字段相同则不调用 Monitor，不触发编辑器重绘。读取、保存确认和其他记录的变动不再让当前项回查 DataSet。数据集列表排序、成员关系和全量查询比较仍由 DataSet 维护，不声称已消除这些处理。

界面连续修改三个字段时，来源保存“确认值 + 所有在途与排队修改”的最终视图。第一项确认只替换底层确认值，后两项继续叠加并保持可见；最终视图未变化不重复通知。失败只撤销对应操作的覆盖层，保留后续修改；错误通过同一操作的目标来源交付，编辑器继续保留用户未提交的文字草稿。

Monitor 回调允许继续发起编辑。嵌套更新发生后，来源不再向后续接收者交付外层旧快照；取消后不接收迟到回调，新注册者只接收当时的最新快照。配置换代关闭旧来源，关闭数据集解除全部记录 Monitor，不产生新的 Core 查询。

* 项目运行中的定向刷新与结构更新

单任务的标题、状态、正文和清单直接通过 DataSet 的 ~taskSource(rowId).monitor()~ 更新；项目容器不监听这些字段后逐项回查。DataSet 合并完整确认事件和所有待提交字段后，先推进全部来源快照，再定向通知实际变化的记录。排序键与文件版本仅作为上下文推进，不单独引起任务控件重绘；排序结果变化仍触发容器结构事件。

~subscribeStructure~ 只交付稳定行成员、源顺序、层级、普通标题／任务类别以及 ARCHIVE／VISIBILITY 变化。项目页面只在这些变化时归并章节，文档容器只在结构或筛选命中身份变化时重算可见路径；普通字段确认、无关任务编辑会话结束不触发容器遍历。当前有输入草稿时延迟应用结构和当前章节的外部快照，会话结束后只处理已积累的变化。

同文件移动仍提交已有 Movement，Core 负责保真写回及父子树的真实变化。DataSet 按整批 before／after 身份映射保留稳定行及来源对象，消费 Core 的排序键与最新层级后重排章节；任务控件继续沿用同一个 Monitor。新增、删除和重名出现序号变化也走同一入口，不增加页面查询或 Core 对外协议。

事件缺少 after.view 或确认版本不连续时，不消费半批内容，由管理器合并恢复查询。项目通过 ~subscribeFiles~ 接收一次性完整文件，更新导言、原文和链接索引，读取失败保留当前文档。编辑期间暂存完整文件；应用前若任务已推进到更新版本，重新请求同版本文件，不以旧完整快照覆盖新任务。

任务事件未携带完整的 documentSections.linkTargets，运行中的普通修改只标记链接索引待确认；实际执行内部跳转时，通过管理器按需读取完整文件并替换链接目标投影，保留文档会话、控件键和滚动位置。宿主不从标题或正文猜测 Org 目标。只读原文仍表示打开或完整恢复时的源文本，普通任务增量不在 ArkTS 拼接 Org 原文。
