* 结论

模拟器已在关闭 WebDAV 的独立本地仓库复现长时间“正在读取任务”。主要耗时集中在内存中的任务投影与重复标题路径定位，磁盘扫描和 Org 正文读取并非本轮主要耗时。项目页面继续按每次打开查询一次的要求评估，不提出持久化项目缓存方案。

定位到三个问题：

1. ~tasks_from_file~ 为每个节点调用 ~task_edit_content~ ，后者每次先调用 ~path_headlines~ ，重新构造整份文件的标题路径列表后才查找当前节点。节点数为 N 时，一轮完整任务投影包含 N 次完整标题遍历，形成接近 O(N²) 的计算。首页查询约 4.90 秒，其中 ~task_edit_content~ 合计约 4.65 秒。
2. 项目页面的四项查询虽然合为一批，但 ~categories~ 查询覆盖整个仓库。即使只打开 35 节点的小项目，同批文件并集仍包含 21 个业务 Org 文件，其他大文件也会完整生成任务投影，项目数据准备约 4.91 秒。完整项目文件的 bridge 投影又调用 ~file.nodes()~ ，重复生成目标文件的全部节点。
3. 修改一条记录仅从磁盘加载目标 Org 一次，仍会生成该文件全部任务投影三次：初始变更日志、执行结果通知、提交完成通知。869 节点文件中一条备注修改约 6.29 秒，其中三轮任务投影约 6.01 秒。

869 节点项目在数据准备完成后还触发 ~THREAD_BLOCK_6S~ ，系统故障栈停留在 ArkUI 控件创建、布局测量链路。数据就绪不等于页面已经完成显示；该次最终未形成可操作的项目页面，进程随后退出。

- 小样本：5 个 Org 文件、50 个标题节点、8,420 字节；所打开项目含 10 个节点。
- 规模样本：21 个 Org 文件、2,814 个标题节点、890,358 字节；最大项目 869 节点，另选 35 节点项目验证界面修改与重复打开。

- 日志不记录凭据、远端地址或用户原文；每次访问记录操作种类与隔离样本路径。日志写入会带来少量额外开销。

* 文件加载与扫描次数

本节“扫描一轮”指一次 ~scan_org_files~ 调用；“目录遍历”指一次 ~read_dir~ ，不把内存中的标题遍历算成磁盘扫描。“正文读取”只统计工作仓库中 Org 文件的实际加载入口；~reset~ 、 ~sync~ 、 ~.orgzlyignore~ 等控制或配置读取另列。

以下项目打开统计来自笔记本真实点击。所有样本目录均为平铺目录，若实际目录有子目录，单轮扫描中的 ~read_dir~ 次数会随目录数量增加。

| 阶段 | Core 查询批次／查询项 | 业务库扫描轮数 | 系统库扫描轮数 | 目录遍历次数 | 工作 Org 正文读取次数 | 不同 Org 文件数 |
|-
| 小样本首页首次读取 | 1 批／15 项 | 1 | 1 | 2 | 6 | 6 |
| 小样本打开项目 | 1 批／4 项 | 1 | 1 | 2 | 5 | 5 |
| 规模样本首页首次读取 | 1 批／15 项 | 1 | 1 | 2 | 22 | 22 |
| 规模样本打开 869 节点项目 | 1 批／4 项 | 1 | 1 | 2 | 21 | 21 |
| 界面完成一条任务，小样本或规模样本 | 0 批／1 个修改组 | 0 | 0 | 0 | 1 | 1 |
| API 修改大文件一条备注 | 0 批／1 个修改组 | 0 | 0 | 0 | 1 | 1 |

首页的 22 份正文为 21 个业务文件加系统废纸篓。项目查询排除了系统废纸篓正文，但分类候选仍使系统库进入扫描；该轮系统库返回零份文件。因此项目是两次扫描调用、21 份正文，不是同一文件重复读 21 次。

一次项目页面查询的实际四项内容：

| 数据集 | 范围与用途 |
|-
| ~tasks~ | 当前项目全部任务，同时返回一次性完整文件 |
| ~matches~ | 当前项目标签与分类命中集合 |
| ~metadata~ | 当前项目文件头与元信息 |
| ~categories~ | 排除特殊文件后的仓库文件集合，用于分类候选 |

文件加载按四项查询所需范围的并集执行，因此最后一项把仅需当前项目的读取扩大为全业务库读取。共享一批查询保证每份文件本批只加载一次，但没有减少这批中无关大文件的任务投影计算。

35 节点项目首次打开与重开各产生同样的一批四项页面查询、业务库与系统库各一轮扫描、21 份业务 Org 读取。因这两组通过 HTTP 导航进入，原始日志还各含一次校验查询：仅扫描目标业务库一轮、读取目标文件一次。包含测试导航校验时，原始总数为 2 批／5 项查询、3 次扫描、22 次正文读取；不能把这次额外读取误判为正常点击的行为。

** 修改时的控制与配置访问

单文件修改窗口中还记录到：

- ~read_optional~ 两次：目标 Org 正文一次，~.orgzlyignore~ 一次；本样本没有忽略配置文件，后者是不存在检查对应的读取尝试。
- ~transaction_read~ 九次：四组 ~reset~ ／ ~sync~ 控制状态检查，共八次，加提交前 ~.orgzlyignore~ 依赖核对一次。
- 没有 ~scan_org_files~ 、目录遍历、全库查询或修改结束后的再次正文读取。
- 提交前的文件身份／版本属性校验不是 Org 正文重读。本次未逐一统计所有 ~stat~ 或底层内核 I/O；本报告的次数限定为已标明的 Core 访问入口。
- 修改导致编辑器重建内存语法树，不应把它算为从磁盘重新加载文件。

* 主要耗时的细分证据

** 首页查询

规模样本中：

| 阶段 | 实测 |
|-
| 业务库扫描与正文读取 | 约 19.14 ms，含本次文件解析 |
| 系统库扫描与文件加载 | 约 2.42 ms，与业务库并发 |
| 所有文件 ~tasks_from_file~ 累计 | 4,833.91 ms |
| 其中 ~task_edit_content~ 累计 | 4,653.95 ms |
| 整批 Core 查询 | 4,903.13 ms |
| Core 请求排队与执行的差值 | 小于 1 ms，未出现同步屏障长时间等待 |

并发阶段的累计值不能直接相加当作墙钟总时长。上述数据足以确认：本轮绝大部分 Core 查询时间消耗在任务投影。

调用链为 ~query_snapshot -> tasks_from_file -> task_edit_content -> path_headlines~ 。~path_headlines~ 返回完整 ~Vec~ ，所以后面的 ~find~ 并不能提前结束整份标题树的构造。869 节点文件的一轮投影会调用该查找 869 次，每次生成整份文件的路径列表；这一层重复遍历就涉及约 755,161 个标题访问，尚未计算其他语法节点、路径分配与文本处理。

对应实现为 [[file:../../core/src/filter.rs][任务投影]]、[[file:../../core/src/model/task_inline.rs][任务编辑内容读取]] 和 [[file:../../core/src/model/task_path.rs][标题路径构造]]。

** 完整项目 bridge 投影

869 节点项目的完整文件投影合计 2,314.89 ms，其中：

| 阶段 | 实测 |
|-
| ~file.nodes()~ 再次生成全部节点 | 2,287.95 ms |
| 普通 HTML 渲染、文档 HTML、分段等其余部分 | 合计约 26.94 ms |
| 整批返回 JSON 长度 | 13,164,196 字节，约 12.55 MiB |
| JSON 编码 | 19.28 ms |

完整文件快照同时携带节点、正文和 HTML 等投影；目标项目节点已存在于同批任务结果，~file.nodes()~ 又计算了一遍。该轮总计生成 3,683 个任务编辑投影，即全库 2,814 个，加目标项目重复的 869 个。重复计算发生在内存，未增加正文读取次数。

对应实现为 [[file:../../harmony/src/bridge.rs][完整文件 bridge 投影]] 与 [[file:../../core/src/model/conflict_preview.rs][文件节点投影]]。

** 单条修改

869 节点文件的单条备注修改，三轮 ~tasks_from_file~ 分别为 2,015.51 ms、1,999.82 ms、1,998.12 ms，共 6,013.45 ms；其中 ~task_edit_content~ 共 5,826.95 ms。目标 Org 仅从磁盘加载一次，三轮共计算 2,607 份节点编辑投影。

三轮来源为文件工作任务的 ~journal.attach~ 、处理 ~FileCommand::Execute~ 时的 ~journal.finish~ 、处理 ~FileCommand::Save~ 完成后的 ~journal.finish~ 。后两处均通过 ~snapshots~ 重建文件全部任务投影，不只处理本次修改的单条记录。

对应实现为 [[file:../../core/src/model/task_operation_executor/file_worker.rs][文件工作任务]] 和 [[file:../../core/src/model/mutation_journal.rs][语义变更日志投影]]。

35 节点项目的界面完成操作也生成三轮投影，共 105 份编辑内容，但 Core 修改仅 41.40 ms。其窗口只有一个修改组，没有查询循环、重复提交或全库扫描。API 与界面修改使用同一 Core 修改入口。

** UI 冻结

首次大项目诊断的系统故障记录：~Reason: THREAD_BLOCK_6S~ ，应用主线程停留在 ~libace_compatible.z.so~ 的 ~CustomNode::Render~ 、 ~FrameNode::Measure~ 、 ~FlexLayoutAlgorithm::Measure~ 等调用中，进程 RSS 约 571,924 kB。

项目文档使用 ~Scroll + Column + ForEach(this.sections)~ 立即构建完整章节及任务控件，并非按可见范围创建。869 个节点使首次布局工作量与内存压力明显扩大。系统栈支持“首次 UI 构建／布局发生阻塞”的判断，不能仅凭该栈把具体开销全部归于某一个 ArkTS 方法。

因此表中的 7,659 ms 只表示项目数据已交给页面；不是用户已经能阅读和操作的时间。首次布局采样只取得系统界面，未取得正常项目控件树，随后 HTTP 连接断开；该组不用于证明修改或页面显示成功。

* 后续修改建议

按以下顺序处理，均可维持“每次打开项目查询一次”，无需持久化项目缓存：

1. 同一次读取中构造标题路径与节点映射，后续直接使用已经取得的 ~Headline~ 生成编辑内容，操作结束即释放；避免每个节点再次遍历整份文件。
2. 完整文件 bridge 投影复用本批已经产生的目标节点结果，避免 ~file.nodes()~ 再生成一遍。同一文件字节和版本边界应继续保留。
3. 修改流程避免为了中间通知和最终通知反复生成相同的完整任务投影；保持变更日志语义与提交后的事件一致性，不改为再次查询全库。
4. 缩小项目分类候选请求的影响，或让该项元信息需求不迫使其他文件生成任务编辑投影；当前项目数据不应等待无关大文件的编辑内容计算。
5. 项目文档按可见范围创建／测量控件，保留章节定位与编辑会话，验证大项目不再触发系统冻结。

这些是诊断后的优化方向，本次没有将其作为功能修复交付。若需要调整 Core 对外接口，仍应先按仓库规范确认接口方案。

* 分类候选移入父级 Manager 后的复验

2026-11-19 后续修改为 DataManager 增加可选 parent；本地没有的 DataSet 名称直接交给父级，子级只负责自己的查询、订阅、刷新、缓存和关闭。全局 categories 复用今天排序原有文件元信息范围，运行期间消费增量；项目本地只保留 tasks、matches 和 metadata 三项，转换项目也使用全局当前分类快照。

|-
