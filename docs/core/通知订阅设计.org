* 职责与数据来源

通知只提供订阅，不属于 ~CoreQuery~ 或 ~CoreQueryResult~ ，没有主动查询、消费或确认接口。完整模块接口与持久化保护见 [[file:文件状态与通知设计.org][文件状态与通知设计]]。

~core::file_state~ 的独立 ~process~ 管理基线与已观察文件的内容版本、存在性和冲突状态。Workspace 启动时并发加载各仓库受保护的基线元数据，等待初始化结果后开放业务；初始化失败保留明确的基线异常状态，不把整个 Workspace 变成不可读。不扫描 Org 文件，也不根据基线路径推断本地文件仍然存在。

搜索、单文件读取、成功提交、同步与 reset 把已有文件信息送入文件服务；服务根据实际版本与基线比较，主动向通知中心推送文件状态。未读取路径保持未知，没有相关文件通知；没有读取过的本地删除也不会仅因基线有该路径就被发现。正常完整搜索可以确认自己成功覆盖范围内已知路径的删除；排除路径、零匹配任务或失败查询不能误作删除证据。

通知状态直接归已有 ~NotificationCenter::process~ 所有。投影文件状态服务和仓库错误模块送来的事实，缓存按仓库维护的通知贡献与各 monitor 最近发送的集合；不读基线、不读正文、不执行合并、不访问网络，也不因文件事件主动查询。普通查询可因观察到新的文件事实而引起通知变化，但不查询通知。

* 订阅契约

~OrgWorkspace.watch_notifications(repo_ids, monitor)~ 接收实现 ~NotificationMonitor~ 的对象，返回 ~Result<NotificationSubscription, CoreError>~ 。 ~repo_ids=None~ 表示全部仓库， ~Some(vec![])~ 表示空范围；未知仓库或已停止的 Workspace 拒绝注册。

注册后立即调用一次 ~snapshot(NotificationSnapshot)~ ，发送当前缓存中的全部通知，包括空列表。随后异步向文件服务请求内存快照进行对齐，不触发任何文件读取。首次空列表仅表示当前已知通知为空，不保证全部文件已被检查。以后仅在该范围内的通知集合变化时调用 ~changed(NotificationDelta)~ 。

~NotificationDelta~ 包含 ~from_revision~ 、 ~revision~ 与 ~Added / Removed / Updated~ 变化。通知按枚举类型及完整数据确定身份，完全相同才是同一通知。 ~Updated~ 带完整 before、after，等价于同批移除旧值并加入新值；基线异常原因改变使用该形式。没有变化不回调，新增订阅不会让其他 monitor 重复收到快照。

通知顺序按稳定 Core 仓库 ID、类型与文件路径排列，基线异常排在同仓库文件冲突前，唯一 ~SyncRequired~ 置末。顺序不属于通知身份。 ~NotificationDelta.apply~ 按完整值原子应用变化并恢复该顺序，拒绝不连续或倒退版本；版本只表示运行时顺序，不持久化。回调不得同步等待当前 Workspace 的后续业务命令。

多个来源贡献同一通知时只显示一次。清除某个文件或仓库的贡献，不得清除另一来源仍需要的提示。先按 monitor 的仓库范围选择贡献，再去重，不能从去重后的全局提示反推所属仓库。句柄析构取消订阅，取消后不发送迟到快照或增量。

* 分类型规则

| 类型 | 依据 | 清除条件 |
|-
| ~SyncConflict~ | 已观察到的当前文件含 ~CONFLICT~ 容器，每文件一条 | 更新状态不再含冲突，或确认删除、reset、移除仓库 |
| ~SyncRequired~ | 有效远端基线下至少一个已观察文件的当前状态不同 | 范围内所有已知差异消失，或 reset 清除基线 |
| ~SyncBaselineUnavailable~ | 受保护的基线加载失败，携带仓库 ID 与脱敏原因 | 后续业务重新加载成功或 reset 清除基线 |

仓库从未建立基线时不生成 ~SyncRequired~ 。基线不可用不能当作首次同步或无修改；该仓库撤销无法确认的待同步贡献并产生基线异常，其他仓库的贡献保留。冲突依据实际文件信息，仍可独立展示。恢复到基线的原始字节后重新比较可清除提示，不使用只置为真的 dirty 标志。

* 仓库错误通知

每个 Workspace 持有一个 ~RepositoryErrorManager~ ，由它维护当前仓库错误列表。仓库打开和扫描逻辑负责确认错误或恢复，并向该模块报告。错误列表的内容变化时，模块向 ~NotificationCenter~ 推送完整快照，包括清空后的空列表。通知中心缓存这个来源的通知贡献，结合文件状态贡献，为各订阅者比较新旧通知集合。

** Core 内部接口

#+begin_src rust
pub(crate) struct RepositoryRootObservation {
    pub(crate) directory: String,
    pub(crate) epoch: u64,
    pub(crate) revision: u64,
}

pub(crate) enum RepositoryError {
    RootMissing,
}

pub(crate) enum RepositoryErrorKind {
    RootMissing,
}

pub(crate) struct RepositoryErrorEntry {
    pub(crate) root_directory: String,
    pub(crate) error: RepositoryError,
}

pub(crate) struct RepositoryErrorSnapshot {
    pub(crate) revision: u64,
    pub(crate) errors: Vec<RepositoryErrorEntry>,
}

impl RepositoryErrorManager {
    pub(crate) fn configure(&self, roots: BTreeMap<String, u64>) -> Result<(), CoreError>;
    pub(crate) fn report(
        &self, observation: RepositoryRootObservation, error: RepositoryError,
    ) -> Result<(), CoreError>;
    pub(crate) fn clear(
        &self, observation: RepositoryRootObservation, kind: RepositoryErrorKind,
    ) -> Result<(), CoreError>;
    pub(crate) async fn flush(&self) -> Result<(), CoreError>;
}

impl NotificationCenter {
    pub(crate) fn repository_errors(
        &self, snapshot: RepositoryErrorSnapshot,
    ) -> Result<(), CoreError>;
}
#+end_src

| 业务触发 | 仓库错误模块的处理 |
|-
| 打开或扫描时确认配置根目录返回 ~NotFound~ | ~report~ 写入 ~RootMissing~ ，重复观察同一错误只保留一条 |
| 目录恢复，通过仓库身份校验并完成扫描 | ~clear~ 移除这个目录的 ~RootMissing~ |
| 仓库配置被移除或替换 | ~configure~ 批量移除旧配置的错误及观察记录，新目录根据后续扫描结果独立处理 |

错误按配置根目录和错误类型标识，冷启动尚未取得 Core 仓库 ID 时就可以记录。首个接入的类型为 ~RootMissing~ 。确认缺失的仓库退出本次读取，其他仓库继续扫描。保存配置但扫描尚未成功时保留该目录已有的缺失错误。权限错误、仓库身份异常和单个 Org 文件缺失分别沿用业务的错误语义。工作区关闭后释放内存状态，下次启动由实际观察生成错误。

** 顺序与通知增量

Workspace 在独占配置命令内汇总各目录的打开结果，登记有效配置后上报缺失。查询开始扫描时携带对应目录的 ~epoch~ 和递增 ~revision~ 。错误模块只接受当前 ~epoch~ 下对应错误键的较新观察。清除一条错误后仍记录该键的最新序号，防止迟到结果重新加入旧错误。目录从配置移除后再次加入时分配新 ~epoch~ 。

错误模块串行应用命令。列表内容变化时，按目录和错误类型输出一份完整快照，使用递增的来源版本。通知中心收到较新的快照后替换该来源的贡献。对每个订阅者，错误键新出现时发送 ~Added~ ，键消失时发送 ~Removed~ ，同一键的内容改变时发送 ~Updated~ 。错误列表清空时撤销这个来源的全部贡献。订阅者继续用 ~NotificationSnapshot~ 获取首次快照，用 ~NotificationDelta~ 接收后续变化。

前述更新接口成功返回代表消息已入队。需要等待分发的业务先等待 ~RepositoryErrorManager::flush~ 确认快照已入通知队列，再等待 ~NotificationCenter::flush~ 确认已处理。关闭 Workspace 时先结束业务，再排空仓库错误模块和文件状态服务，最后排空通知中心。

** 订阅范围

~RootMissing~ 投影为 ~CoreNotification::RepositoryRootMissing { root_directory }~ ，序列化为 ~{ type: "repositoryRootMissing", rootDirectory }~ 。~OrgWorkspace.watch_notifications_with_scope(scope, monitor)~ 按两组目录分别匹配。 ~NotificationScope.repository_error_roots~ 接收所有需要监听错误的配置目录，覆盖纯本地和 WebDAV 仓库。 ~NotificationScope.sync_roots~ 接收需要汇总同步类通知的 WebDAV 配置目录。各范围的空列表表示该范围为空。Harmony 通过已有通知回调向 ~NotificationManager~ 传递快照和增量。

* 事件顺序与生命周期

文件服务只在内存中处理普通更新、删除与查询。实际读盘或提交结果在仓库锁内取得 revision；每文件分别比较 revision，删除记录同样保留顺序，文件 A 的新事件不能丢弃文件 B 的有效观察。仓库配置 epoch 排除已移除或更换根目录前的结果。启动加载不能覆盖已由同步提交的新基线。

修改先完整提交，再把文件元信息与 ~after_version~ 交给文件服务；等待状态事件入队后才发送既有任务数据事件。通知处理 process 为 ~DataChangeEvent::NotificationEvent~ 附加当前仓库通知缓存，不为填充字段查询通知。同步把本轮已读取内容与成功事务字节缓存合并，再连同实际保留的基线原子提交；失败与取消也保留已确认远端事实，不额外扫描。

同步与 reset 先更新通知，再发送 ~ExternalFileChanged~ 。文件服务 ~flush~ 确认此前命令产生的事件已入通知队列，通知中心随后确认回调完成；通知 process 不等待文件服务 reply。停止时先结束业务，再停止文件服务加载和排空状态输入，最后排空仓库错误、文件状态及通知回调。

* Harmony 接入

Rust bridge 把两个 monitor 方法编码为 ~type: snapshot | changed~ 的 JSON 对象；为仓库通知附加 ~rootDirectory~ ，C ABI 与无界 FIFO TSFN 保序传递。ArkTS 的 ~NotificationManager~ 对每个订阅维护 native revision 和通知数组，按完整值应用整批变化，再发布内存快照或携带快照的增量；无变化不发布，过期生命周期回调不回写，版本不连续保留最近快照，不主动查询。

EntryAbility 启停应用级订阅。配置变化重绑，恢复前台只重试异常订阅。仓库目录错误覆盖所有已配置仓库。同步类通知覆盖启用 WebDAV 且远端地址非空的仓库，显式空范围保持为空。页面通过 ~NotificationManager.watch~ 直接注册监听，先获得最近的内存快照，再接收增删改及应用增量后的快照。组件销毁时解除监听。角标和退后台同步通过 ~NotificationManager.subscribe~ 接收当前绑定的已确认快照，包括空列表。重绑期间角标和退后台同步的订阅等待本轮首次快照，页面保留最近成功内容。尚未读取文件的修改可能不触发自动同步，手动同步仍处理正常同步范围。
